BullMQ v5 · Redis

Aprender BullMQ jugando su infraestructura

BullMQ no es difícil porque su API sea complicada: es difícil porque su comportamiento real no está en la API, sino en doce scripts Lua y ocho estructuras de Redis. Estos seis juegos atacan exactamente esa capa oculta, cada uno con una palanca de repetición.

01 — El problema real

La API promete una cosa; Redis ejecuta otra

El único modo serio de aprender esto es ver las estructuras de datos moverse. Estos son los cuatro sorpresas que un simulador visual elimina de raíz.

La prioridad no salta la cola

En moveToActive-11.lua, el FIFO gana: el script hace RPOPLPUSH wait → active y solo si la lista wait queda vacía consulta el set priorizado con ZPOPMIN. Un job con priority: 1 added después de 20 jobs sin prioridad se procesa el último de los 21.

La razón: priority: 0 significa "sin prioridad explícita" y va a la lista; cualquier valor >0 va al ZSET. Son dos colas distintas, no un orden único.

El score del ZSET está empaquetado

La prioridad no se guarda como número plano. getPriorityScore calcula priority * 0x100000000 + contador para que el desempate dentro de la misma prioridad sea FIFO. El delayed usa otro truco: el score es (timestamp + 1) * 0x1000 - 1.

Por eso ZRANGEBYSCORE delayed 0 (ts+1)*0x1000-1Promotion puede traer de golpe hasta 1000 jobs. Un simulador que dibuje el score real enseña esto sin leer el código.

El lock expira y nadie te avisa

Un worker mantiene un lock con TTL sobre el job. Si el proceso muere, el lock caduca y otro worker puede tomar el mismo job. moveStalledJobsToWait-9.lua lo rescata: lo devuelve a wait, incrementa stc, y si supera maxStalledCount lo marca como fallido con "job stalled more than allowable limit".

Es at-least-once delivery: un job puede ejecutarse dos veces. Tu processor debe ser idempotente, y casi nadie lo internaliza hasta que le explota en producción.

La atomicidad vive en Lua, no en Node

Cada transición de estado es un script Lua que corre dentro de Redis: mover a active, asignar lock, contar intentos, emitir el evento al stream y renovar el marcador, todo en una sola operación indivisible.

Reescribir esa lógica en TypeScript — aunque "se vea igual" — abre carreras entre workers. Ver los dos modelos competir en pantalla es el juego que más rápido lo enseña.

03 — Catálogo

Seis juegos, seis capas de la infraestructura

Cada uno ataca un mecanismo distinto de BullMQ y aporta una forma distinta de repetición. Todos comparten el mismo motor de simulación, de modo que el segundo juego arranca con el primero ya construido.

JUEGO 01 El Puerto de Redis

Un muelle con tres zonas visibles: wait, prioritized y delayed. Los jobs llegan como contenedores y tú decides en qué zona entran, con qué score y con qué prioridad.

Mecánica: llega una oleada de contenedores con metas de entrega. Colocas cada job en una zona arrastrándolo. Puntos por no romper el orden FIFO dentro de wait y por mantener el score ZSET bien formado. Pierdes si el score se desordena.

Enseña: la separación LIST/ZSET, el score empaquetado priority × 2³² + contador, la promoción de delayed a wait, y por qué la prioridad no es "saltar la cola".

wait / prioritized / delayed score ZSET promoteDelayedJobs
HTML + Canvas 2D · repeat: rebobinar oleada y reintentar con otro reparto

JUEGO 02 El Guardián del Lock

Eres el lock. Cada worker tiene un candado con TTL sobre el job que procesa. Si el worker se cuelga, el lock caduca y otro worker puede robarle el job.

Mecánica: el juego es el latido. Cada worker debe pulsar "renovar lock" antes de que caduque. Puedes matar un worker a propósito y observar el relevo. Ganas por detectar correctamente los stalled y por empujar el stc por encima de maxStalledCount solo cuando corresponde.

Enseña: lockDuration, renovación a la mitad del TTL, moveStalledJobsToWait, el contador stc, y que la entrega es at-least-once → el processor debe ser idempotente.

locks / stalled maxStalledCount PX / SET NX
HTML + Canvas + requestAnimationFrame · repeat: revancha con otro lockDuration

JUEGO 03 La Carrera de las Transiciones

Dos implementaciones compiten por los mismos jobs: la real (scripts Lua atómicos dentro de Redis) y una naive escrita en el cliente, con lecturas y escrituras separadas.

Mecánica: enciendes las dos implementaciones a la vez sobre la misma cola. La naive duplica jobs, pierde jobs y deja locks colgando. Tu processor tiene que deducir qué script Lua invocó el estado que observas.

Enseña: por qué Redis ejecuta lógica, por qué los scripts son atómicos, qué significa moveToActive como una unidad indivisible, y cómo una reimplementación "equivalente" en Node introduce carreras.

Lua / atomicidad script-loader race conditions
Three.js — dos "servidores" enfrentados, con cilindros visuales · repeat: carrera resimulada con otra semilla

JUEGO 04 El Reloj de los Schedulers

upsertJobScheduler es idempotente por diseño: llamarlo dos veces con el mismo id no duplica nada. Ese detalle se aprende jugando contra el reloj de 24 horas.

Mecánica: una rueda de 24 horas. Colocas jobs recurrentes y eliges every o pattern cron. Compara con el reloj real: every se alinea al reloj, no al momento en que lo configuraste. Los jobs que se solapan se pisan.

Enseña: upsertJobScheduler, alineación al reloj, el offset, pattern cron de 6 campos, la plantilla del job y por qué repeat está deprecado desde 5.16.

job schedulers cron / every upsert idempotente
HTML + Canvas (reloj radial) · repeat: correr el mismo día 60 veces

JUEGO 05 El Muro de la API

Una API externa con límite de peticiones. Tus workers la golpean en paralelo. El limiter de BullMQ es global por cola, no por worker: todos compiten por el mismo cubo.

Mecánica: ajustas limiter.max, limiter.duration y la concurrencia para atravesar el muro. Si el límite se pasa, el proveedor te corta y pierdes. El cubo se llena con INCR + PEXPIRE.

Enseña: rate limiting global vs. por worker, getRateLimitTTL, el early-return cuando expireTime > 0, y cómo concurrency mal puesto desperdicia slots.

limiter global concurrencia INCR / PEXPIRE
HTML + Canvas (medidor de cubo) · repeat: reintentar con otra tasa

JUEGO 06 El Árbol de Dependencias

FlowProducer añade un árbol entero de forma atómica. El padre queda en waiting-children hasta que todos sus hijos completan.

Mecánica: construyes un árbol de trabajo. Alishes hijo falla, el padre puede fallar también o ignorar ese hijo (ignoreDependencyOnFailure). El nivel de anidamiento es libre y los hijos viven en colas distintas.

Enseña: waiting-children, releaseParentIfNoPendingDependencies, getChildrenValues(), la atomicidad del add del árbol completo y el fallo en cascada.

flows / DAG fallo en cascada waiting-children
Three.js (árbol 3D) · repeat: podar una rama y volver a sembrar

Nota sobre el stack: HTML + Canvas 2D cubre los juegos 1, 2, 4 y 5 — son simetrías bidimensionales y DOM/Canvas es más preciso y ligero. Three.js entra donde la tercera dimensión aporta información real: la carrera de transiciones (dos mundos enfrentados) y el árbol de dependencias (profundidad y jerarquía). Usar WebGL donde basta con SVG es sobreingeniería; evitarlo en 4 de 6 juegos mantiene el bundle por debajo de 100 KB y el arranque instantáneo.

04 — Arquitectura

Un solo motor, seis juegos encima

La repetición fiable exige determinismo. El motor central lo garantiza: reloj virtual, sin Math.random sin semilla, y un historial de eventos que permite rebobinar cualquier partida.

Capas del motor

  1. capa 0 Reloj virtual

    El tiempo avanza por ticks discretos, no por Date.now(). Un tick = un paso determinista. Cambiar la velocidad de reproducción no cambia el resultado.

  2. capa 1 Store de Redis simulado

    Implementa LPUSH, RPOPLPUSH, ZADD, ZPOPMIN, ZRANGEBYSCORE, INCR, PEXPIRE, SET ... PX, XADD y HINCRBY con la semántica exacta de BullMQ, incluidos los scores empaquetados.

  3. capa 2 Intérprete de Lua

    Los scripts se ejecutan como pasos atómicos contra el store. Aquí es donde nace la diferencia real: si reimplementas la lógica en el cliente, no eres el mismo sistema — y el juego 3 lo demuestra.

  4. capa 3 Historial y replay

    Cada transición queda grabada con tick, script, keys tocadas y resultado. Eso habilita rebobinar, cambiar un parámetro y reejecutar — la palanca de repetición que comparten los seis juegos.

Por qué el replay importa

Aprender bullMQ no es memorizar la API: es construir un modelo mental predictivo. Ese modelo se corrige con el contraste entre lo que esperabas y lo que pasó. Un simulador que solo corre hacia adelante no permite ese contraste; uno que rebobina y compara, sí.

Por eso cada juego tiene un botón de repetición con una variable distinta: el reparto de prioridades, el TTL del lock, la semilla de la carrera, la hora del día, la tasa del límite, la rama del árbol.

Cómo verificar el simulador

Un simulador que miente es peor que no tener simulador. La validación es straightforward porque BullMQ es observable desde fuera. 

// Test de paridad: mismo escenario, Redis real vs. simulador
const real = await runAgainstRedis(scenario);
const sim  = runAgainstSim(scenario);

expect(sim.states).toEqual(real.states);   // wait/prioritized/…
expect(sim.scores).toEqual(real.scores);   // score exacto del ZSET
expect(sim.events).toEqual(real.events);   // stream XADD

Con Docker y Redis real puedes correr exactamente los mismos escenarios del juego y comparar estado por estado. La suite de paridad es la que garantiza que el simulador enseña BullMQ y no una caricatura.

05 — Ejecución

Orden de construcción

Empieza por el motor y el simulador que ya tienes, no por un juego. Cada entrega deja algo usable y las decisiones de diseño se validan con usuarios reales.

FaseQué se entregaIncluyeDesbloquea
F0 Motor + store Redis simulado Reloj virtual, primitivas Redis, scores reales, historial, replay Suite de paridad contra Redis real en Docker
F1 Simulador web + Juego 01 UI del prototipo de arriba, wait/prioritized/delayed con scores visibles, rebobinado Validar el modelo mental con usuarios antes de multiplicar juegos
F2 Juegos 02, 04 y 05 Locks y stalled, schedulers con reloj, rate limiter global Los tres mecanismos que más se confunden en producción
F3 Juegos 03 y 06 en Three.js Carrera de transiciones, árbol de dependencias Atomicidad y flows, los dos temas de mayor profundidad
F4 Modo retos Retos guiados, casos que rompen la intuición, ranking local Uso sostenido más allá del tutorial

Stack recomendado

TypeScript · Vite · Canvas 2D
Three.js solo en J03 y J06
Node + Docker para la paridad

Sin servidor

Todo corre en el navegador. La paridad con Redis real se ejecuta en CI, no en la experiencia del jugador. Cero infraestructura, cero fricción para probar.

Riesgo principal

Que el simulador enseñe una versión simplificada. Se mitiga con la suite de paridad: si el score, el estado y el stream no coinciden con Redis real, el build falla.
